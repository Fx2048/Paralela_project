Paralela Project

Entrenamiento distribuido de redes neuronales mediante Data Parallelism y PyTorch DDP

1. Problema

El entrenamiento de redes neuronales profundas es un proceso computacionalmente intensivo. A medida que los modelos y los datasets crecen, el tiempo requerido para completar el entrenamiento en una sola GPU puede aumentar considerablemente.

El desafío principal consiste en acelerar el proceso de entrenamiento sin degradar la calidad del modelo (accuracy), aprovechando múltiples GPUs de forma eficiente.

Sin embargo, la paralelización introduce costos de comunicación, sincronización y coordinación que impiden alcanzar un speedup ideal.

Este proyecto aborda el problema mediante la implementación de Data Parallelism utilizando PyTorch DistributedDataParallel (DDP) sobre dos GPUs, midiendo el speedup y la eficiencia paralela obtenidos.

2. Objetivos

  1. Implementar un entrenamiento baseline secuencial de ResNet18 sobre CIFAR-10 utilizando una sola GPU.
  2. Implementar el mismo entrenamiento de forma distribuida mediante PyTorch DDP con 2 GPUs.
  3. Comparar tiempos de ejecución, accuracy de entrenamiento y accuracy de prueba entre ambas versiones.
  4. Calcular speedup, eficiencia paralela y la brecha respecto al tiempo ideal.
  5. Demostrar que la paralelización reduce significativamente el tiempo de entrenamiento sin sacrificar la calidad del modelo.
  6. Relacionar los resultados experimentales con conceptos de computación paralela como la Ley de Amdahl, overhead de comunicación y operaciones colectivas.

3. Marco teórico

Data Parallelism

En Data Parallelism, el dataset se divide entre múltiples dispositivos. Cada GPU mantiene una réplica completa del modelo y procesa un subconjunto diferente del batch.

Después del cálculo de gradientes se realiza una sincronización, normalmente mediante una operación colectiva ALLREDUCE, para que todas las réplicas actualicen sus pesos de forma consistente.

PyTorch DistributedDataParallel (DDP)

DDP es la API de PyTorch utilizada para implementar entrenamiento distribuido.

  • Cada proceso controla una GPU.
  • DistributedSampler particiona el dataset entre los procesos.
  • DDP sincroniza automáticamente los gradientes después de loss.backward().
  • Las réplicas mantienen pesos consistentes mediante la sincronización de gradientes.

Métricas de rendimiento paralelo

Speedup:

S = T₁ / TN

Eficiencia:

E = S / N

Estas métricas permiten cuantificar qué tan efectiva es la paralelización y qué tan cerca se encuentra el sistema del speedup ideal.

5. Arquitectura

El esquema de paralelismo implementado corresponde a Data Parallelism.

Dataset CIFAR-10 │ ▼ DistributedSampler / \ / \ GPU 0 GPU 1 Batch 64 Batch 64 │ │ ▼ ▼ ResNet18 ResNet18 │ │ ▼ ▼ Gradientes Gradientes \ / \ / ─── ALLREDUCE ─── │ ▼ Gradientes sincronizados │ ▼ Actualización de pesos

El batch global de 128 muestras se distribuye entre las dos GPUs:

128 = 64 + 64

Cada GPU mantiene una copia del modelo y procesa una porción diferente de los datos. Después del backward(), DDP sincroniza los gradientes mediante operaciones colectivas.

9. Speedup

El speedup se calcula comparando el tiempo del entrenamiento secuencial con el tiempo del entrenamiento distribuido.

Speedup = 667.2 / 389.6 ≈ 1.71×

Por tanto, utilizar dos GPUs permitió alcanzar un speedup de aproximadamente 1.71×.

El tiempo de entrenamiento se redujo aproximadamente:

Reducción = (667.2 - 389.6) / 667.2 × 100 ≈ 41.6 %

Comparación con el speedup ideal

  • Speedup ideal con 2 GPUs: 2×
  • Speedup real: 1.71×
  • Diferencia respecto al ideal: 0.29×

El sistema no alcanza el speedup ideal debido a los costos asociados a comunicación, sincronización y coordinación entre los procesos distribuidos.

10. Eficiencia

E = 1.71 / 2 ≈ 85.5 %

La eficiencia paralela obtenida fue aproximadamente 85.5 %.

Esto indica que una proporción elevada de la capacidad computacional adicional de la segunda GPU fue aprovechada para acelerar el entrenamiento.

11. Brecha respecto al tiempo ideal

Si el speedup fuera perfectamente lineal, el tiempo esperado con dos GPUs sería:

Tideal = 667.2 / 2 = 333.6 s

Sin embargo, el tiempo real observado fue:

Treal = 389.6 s

Por lo tanto, la diferencia respecto al tiempo ideal es:

389.6 - 333.6 = 56.0 s

Esta diferencia debe interpretarse como una brecha respecto al rendimiento ideal, y no como un costo exclusivamente de comunicación.

Entre los factores que contribuyen se encuentran:

  • Operaciones colectivas ALLREDUCE.
  • Comunicación entre procesos.
  • Sincronización mediante barrier.
  • Particionamiento del dataset mediante DistributedSampler.
  • Coordinación de los procesos de entrenamiento.
  • Overhead general del runtime distribuido.
Conclusión:
Paralelismo no significa velocidad ideal. Al aumentar el número de recursos computacionales también aparecen costos de comunicación y coordinación.

Este comportamiento es consistente con los principios de la Ley de Amdahl y con los costos asociados a las operaciones colectivas en sistemas paralelos.

12. Conclusiones

  1. Se implementó exitosamente Data Parallelism mediante PyTorch DistributedDataParallel utilizando dos GPUs NVIDIA T4.
  2. El tiempo de entrenamiento se redujo de 667.2 s a 389.6 s, obteniendo un speedup de 1.71×.
  3. La eficiencia paralela alcanzó aproximadamente 85.5 %.
  4. La precisión del modelo se mantuvo comparable: 90.54 % en el baseline frente a 90.99 % en DDP.
  5. La diferencia de 0.45 puntos porcentuales no representa un deterioro del rendimiento predictivo.
  6. La diferencia de 56.0 s respecto al tiempo ideal evidencia los costos asociados a comunicación, sincronización y coordinación.
  7. Los resultados demuestran experimentalmente conceptos de Computación Paralela como speedup sublineal, eficiencia menor al 100 %, operaciones colectivas y overhead de coordinación.
Conclusión general:

El experimento demuestra cuantitativamente que el entrenamiento distribuido mediante PyTorch DDP permite reducir significativamente el tiempo de entrenamiento de una red neuronal utilizando dos GPUs, manteniendo una calidad de clasificación comparable al entrenamiento secuencial.

El speedup obtenido fue de 1.71×, con una eficiencia de 85.5 %, demostrando que el paralelismo es efectivo aunque no alcanza el rendimiento lineal ideal debido a los costos de comunicación y sincronización.
